# Atlas Supabase Deployment

Atlas reads and writes operational data through the server, keeping the Supabase service-role key out of the Expo bundle. Before publishing, apply [`supabase/atlas_schema.sql`](../supabase/atlas_schema.sql) in the Supabase SQL Editor, then use [`supabase/atlas_initial_access.template.sql`](../supabase/atlas_initial_access.template.sql) to create the first facility and manager access record. Add `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` in the deployment environment. The public anonymous key is used only for project validation and must remain protected by Supabase Row Level Security; Atlas itself uses the service role from the server for controlled operations.

The first operational user requires a member record. Insert the authenticated user’s Manus numeric user ID into `atlas_members` with one of the supported roles, a display name, and any facility UUIDs they may access. The mobile workspace returns an **awaiting role assignment** state until that record exists. This intentional gate prevents a newly authenticated user from reading or recording industrial data before authorization is established.

The schema enables Row Level Security on all Atlas tables and intentionally omits anonymous policies because the Expo client does not query Supabase directly. All workspace, sync, intelligence, and approval calls route through authenticated server procedures, which evaluate the Atlas role matrix before data access or mutation.

The same schema now includes `atlas_operational_controls`, `atlas_evidence`, and `atlas_telemetry`. Populate operational controls from approved production, inventory, quality, and safety sources; each record should include a facility scope, domain, status, severity, and whether verification requires evidence. Atlas only allows authorized roles to verify a live control, and a required-evidence control routes operators through the guided inspection workflow.

Photo and audio evidence is copied into the app’s protected local evidence queue first. When the user is authenticated and online, Atlas sends the file to the server-only storage route, persists the resulting object key and URL in `atlas_evidence`, and then removes the local copy. Keep individual evidence files below **16 MB**. The Expo client never receives the storage credentials or the Supabase service-role key.

Telemetry integrations should write time-stamped values into `atlas_telemetry` using one of the supported metrics: `temperature_c`, `vibration_mm_s`, `runtime_hours`, or `pressure_bar`. Atlas derives a transparent low, medium, or high maintenance signal from its configured observation bands and displays the current measurement, confidence, explanation, and recommended human action. Do not use this signal to trigger automatic shutdowns or irreversible changes without a separate approved control workflow.
